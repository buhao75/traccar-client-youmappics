## What This App Does

This app is **YouMapPics**, a private side-project fork of the open-source Traccar Client, rebranded
from the sibling **SAIMOS Guard** app (`C:\_gitea\saimos-cc\traccar-client`) which this repo was
originally imported from. Its home screen is a WebView embedding a **MapStore/GeoStore-backed
web application** (see "MapStore WebView" below for the auth flow and implementation) — that's the
primary, user-facing surface of the app.

Underneath that, it's built on Traccar Client: a Flutter GPS tracking app (Android/iOS) that sends
device location to a Traccar server. Key capabilities: background tracking via
`traccar_client_sdk`, Firebase push commands for remote control, QR code/deep link config import,
optional password protection, and home screen quick actions.

There's also an older native Android reference implementation at
`C:\_github\traccar-client-android_youmappics` (applicationId `org.mistit.youmappics`, note the
different prefix — this Flutter app deliberately uses `de.mistit.youmappics` instead, matching
SAIMOS Guard's `de.mistit.*` convention) — this
Flutter app supersedes it, but it's useful as ground truth for backend URLs, branding colors, and
the exact GeoStore/device-registration request shape (`SaimosccWebview.kt`).

## Architecture

The app is organized into three layers:

**Service layer** (`lib/`)
- `geolocation_service.dart` — thin wrapper around `TraccarClientSdk` singleton; exposes `start()`, `stop()`, `isTracking()`, `requestPosition()`, `getLogs()`
- `preferences.dart` — all config persistence via `SharedPreferencesWithCache`; builds `Config` objects passed to the SDK; Android uses the native SharedPreferences backend for performance
- `push_service.dart` — Firebase Cloud Messaging; handles remote commands (`positionSingle`, `positionPeriodic`, `positionStop`, `factoryReset`) and uploads the FCM token to the server
- `configuration_service.dart` — parses `org.traccar.client://` URIs and HTTP/HTTPS config URLs, applies settings, restarts tracking
- `password_service.dart` — optional password protection stored in SharedPreferences (migrated away from secure storage)

**UI layer** (`lib/`)
- `map_screen.dart` — **the app's home screen**: MapStore WebView; AppBar has refresh and settings icons (settings navigates to MainScreen)
- `main_screen.dart` — tracking toggle card + settings card; reached via the gear icon in MapScreen
- `settings_screen.dart` — all preferences (URL, device ID, accuracy, interval, distance, angle, wakelock, stop detection); contains QR code import entry
- `status_screen.dart` — real-time SDK log viewer, auto-refreshes every 5 seconds, supports share/clear
- `qr_code_screen.dart` — `mobile_scanner` based QR reader; graceful fallback on permission denial

**Infrastructure**
- `main.dart` — initializes Firebase, loads preferences, wires deep links via `app_links`, shows rate dialog
- `quick_actions.dart` — registers home screen shortcuts (start, stop, SOS)
- `firebase_options.dart` — auto-generated by `flutterfire configure`; currently **unused** (`main.dart` calls `Firebase.initializeApp()` without passing `options:`, so init relies purely on the native `google-services.json`/`GoogleService-Info.plist` configs) and stale (still points at SAIMOS Guard's Firebase project, inherited from the import — the native config files were already swapped for YouMapPics' own project, but this generated file wasn't touched since nothing reads it) — do not edit manually, regenerate via `flutterfire configure` if it's ever wired back in
- `lib/l10n/` — 14+ language `.arb` files; English (`app_en.arb`) is the source of truth; run `flutter gen-l10n` to regenerate (handled automatically by build)

## MapStore WebView

Implemented in `lib/map_screen.dart` — ported from the SAIMOS Guard Flutter app, which itself was
ported from `SaimosccWebView.kt` (see the native reference project
`C:\_github\traccar-client-android_youmappics`, class `SaimosccWebview.kt`, for this app's specific
backend conventions).

- Entry point: **the app's home screen** (MapScreen is `home` in `main.dart`)
- Navigation: settings (gear) icon in the AppBar → MainScreen; no separate "Map" button
- Settings: at the very bottom of `settings_screen.dart` — server URL, user, password (keys: `saimoscc_url`, `saimoscc_user`, `saimoscc_password` — internal key names inherited from the SAIMOS Guard import, not renamed); heading: "YouMapPics"
- Auth flow: app info fetch (`appupdates/youmappics.json`, non-fatal) → GeoStore login (Basic Auth) → device registration (legacy Talend GET job, `saimosws/services/manage_tracking_deviceid`) → user details (XML→JSON) → localStorage injection → load WebView
- The device-registration flow also tries a `cc-db-communicator` POST endpoint first (SAIMOS CC-specific, inherited from the import) — this backend doesn't run that service, so it always 404s and falls through to the legacy GET job harmlessly. Fine to leave as dead weight; remove if it turns out to add a noticeable startup delay.
- Geolocation: auto-granted on Android via `setGeolocationPermissionsPromptCallbacks`; native on iOS
- SSL: HTTP calls trust all certificates (`badCertificateCallback`); no VPN requirement — the backend (`wildkogel.steigemann.de`) is reachable over the open internet
- Reference native Android project: `C:\_github\traccar-client-android_youmappics`

**Backend defaults (first run, set in `preferences.dart`):**
- Traccar tracking server: `https://wildkogel.steigemann.de/gt/` (trailing slash required — the bare path 301-redirects via nginx, which the SDK doesn't follow for position POSTs; found via a real-device test, see "Current Status")
- MapStore/GeoStore URL: `https://wildkogel.steigemann.de/ms/#/context/youmappics-mobile/178`

**JDK:** `JAVA_HOME=C:\app\java\jdk-21.0.11+10_x64_jdk` (JDK 21, `javac.exe` present). Android Studio 2026.1.1 is installed.

**Emulator — no working option on this machine (confirmed 2026-07-27):**
- x86_64 emulator (`Medium_Phone_API_35`) won't start — VT-x/AMD-V not enabled in BIOS.
- ARM64 system image (`Pixel_ARM64` AVD) was installed and tried as a workaround — it does **not**
  run either: `PANIC: Avd's CPU Architecture 'arm64' is not supported by the QEMU2 emulator on
  x86_64 host.` ARM64 system images don't run on x86_64 hosts at all, independent of BIOS
  virtualization settings — this is a dead end, don't retry it.
- Only real option for UI testing right now: a physical Android device connected via `adb`.

## Branch strategy

Matches SAIMOS Guard's convention: `main` is a **clean mirror of upstream** `traccar/traccar-client`
(currently tracking `upstream/main` via a remote named `upstream`) — never commit YouMapPics changes
there. All YouMapPics-specific work lives on `youmappics/vX.Y.Z` branches, based on an upstream tag
(currently `youmappics/v10.0.7`, based on upstream tag `v10.0.7`). To pull in a future upstream
release: `git fetch upstream`, then merge/rebase the new tag into a new `youmappics/vNEXT` branch (or
the current one, if staying on the same major line) — normal `git merge` conflicts only arise in
files YouMapPics itself modified (theme color, preference defaults, IDs, a few `.arb` strings); the
WebView/GeoStore additions are new files upstream doesn't touch at all.

**Note on this repo's history:** unlike SAIMOS Guard (a real `git clone` of upstream from the start),
this repo was originally created via a snapshot import (no shared history) — retrofitted onto proper
upstream tracking on 2026-07-28 by rebasing the accumulated rebrand diff onto the `v10.0.7` tag and
resetting `main` to the real upstream `main` (force-pushed, confirmed with the user first since it
rewrites the previously-pushed `main` history).

## Build & Release

**App identity:** Both platforms run under the bundle/package ID `de.mistit.youmappics`. The
internal Android namespace (`org.traccar.client` — Kotlin package structure, MethodChannel names
like `org.traccar.client/file_picker`, deep-link scheme `org.traccar.client://`) is deliberately
left unchanged, inherited from Traccar Client/SAIMOS Guard; it doesn't need to match
`applicationId`.

Builds are intended to run on **Codemagic** (CI service, UI workflow editor, no `codemagic.yaml` in
the repo), same as SAIMOS Guard — not yet set up for this repo (see "Open items" above).

### Local Android build (for testing)

```bash
flutter build apk --debug   # or --release, if a keystore is configured (see below)
```

Install on a connected device (preserves app settings):
```bash
adb -s <device-id> install -r build\app\outputs\flutter-apk\app-debug.apk
```
**Don't** use `flutter install` — internally it does `adb uninstall` + `adb install` and wipes all app data. `adb` lives at `%LOCALAPPDATA%\Android\sdk\platform-tools\adb.exe`.

Note: if `applicationId` ever changes again (e.g. a future rebrand), Android treats it as a completely new app — not an update of the old install, and none of the old settings carry over.

### Android — signed release APK for testers

No keystore exists yet (`android/app/build.gradle.kts` falls back to unsigned without `key.properties`).

1. Generate once, locally (keep the password safe — without the keystore, future updates become impossible):
   ```bash
   keytool -genkeypair -v -keystore youmappics-release.jks -keyalg RSA -keysize 2048 -validity 10000 -alias youmappics
   ```
2. Store in Codemagic: App settings → Android code signing → upload the `.jks` as a Secure File, passwords/alias as encrypted environment variables
3. Set the workflow build mode to Release (`flutter build apk --release`)
4. After a successful build: download `app-release.apk` from the Codemagic build artifacts and send it directly to testers (no Play Store needed; testers must allow "install from unknown sources")

### iOS — TestFlight via Codemagic

**Prerequisites (App ID/App Store Connect app not yet created — see "Open items" above):**
- `DEVELOPMENT_TEAM` in `ios/Runner.xcodeproj/project.pbxproj` (3 occurrences) — `6X2SXDTM5K`, same team as SAIMOS Guard (reverted back to this on 2026-07-28, see "Open items" point 3 for the back-and-forth history).
- `PRODUCT_BUNDLE_IDENTIFIER` (3 occurrences) = `de.mistit.youmappics` (already done)
- App ID `de.mistit.youmappics` registered in the Apple Developer Portal, **Push Notifications capability enabled** (Identifiers → select the app → check "Push Notifications" → Save)
- App created in App Store Connect (bundle ID must match exactly)
- Codemagic: use SAIMOS Guard's existing App Store Connect API key integration for this workflow (same team) — not the separate `64AX396SPH`/`XD3Q76D3HM` one.

**Codemagic setup:**
1. Create an App Store Connect API key (App Store Connect → Users and Access → Integrations → Keys, role "App Manager"), note the `.p8` file + Key ID + Issuer ID (the file can only be downloaded once)
2. In Codemagic: Team settings → Integrations → App Store Connect → add the API key
3. Workflow: set iOS code signing to "Automatic" with this API key, set the **distribution type to "App Store"** (not "Development" — otherwise the upload fails with error 90161 "Invalid Provisioning Profile")
4. Set the build mode to Release; Codemagic then automatically calls `flutter build ipa --release --export-options-plist ...` (no more manual `--no-codesign`)
5. Enable Publishing → App Store Connect, link the same API key, check "Submit to TestFlight", choose the testing group

**One-time, in App Store Connect:**
- Export compliance question on first upload: choose "Standard encryption algorithms …" (the app only uses regular HTTPS/TLS). To skip this prompt on future uploads, add `ITSAppUsesNonExemptEncryption = false` to `ios/Runner/Info.plist` (not yet added here — carry over from SAIMOS Guard if it saves the prompt).
- For **external** testing, a feedback email plus name/phone/email for Beta App Review must be filled in at `https://appstoreconnect.apple.com/apps/<app-id>/testflight/test-info`, followed by an Apple review wait (~24–48h). **Internal** testing (App Store Connect team members) doesn't need this and is available immediately.

**Build number:** Every successful upload to App Store Connect permanently "consumes" the build number (the number after `+` in `version:` in `pubspec.yaml`) — re-uploading with the same number fails with error `ENTITY_ERROR.ATTRIBUTE.INVALID.DUPLICATE` ("bundle version must be higher than the previously uploaded version"), even if the previous TestFlight submission never reached testers for other reasons. Bump the number before every new upload, or enable Codemagic's "Increment build number" option.

**Known gotchas, already fixed in SAIMOS Guard, inherited here (see that repo's git history, issue #2, if any of these resurface):**
- `WebViewSSLBypass.swift` existed on disk but was never registered in `project.pbxproj` (missing PBXFileReference/PBXBuildFile/Sources build phase entries) → "Cannot find 'WebViewSSLBypass' in scope"
- The auto-generated "FlutterFire: flutterfire upload-crashlytics-symbols" build phase script aborted the build when the `flutterfire` CLI wasn't installed on the build machine — the script now checks for it itself and skips the symbol upload instead of failing
- iOS's `WKWebView` sends an incomplete default user agent (missing "Mobile/... Safari/..."), which made MapStore reject it as an unsupported browser — `lib/map_screen.dart` sets a real mobile Safari user agent on iOS
- **`WebViewSSLBypass.swift` saga (2026-07-28) — PENDING real-device confirmation of the final fix:** self-signed-cert internal servers failed to load in the iOS WebView. Two native Swift fix attempts failed (exact-class-name `NSClassFromString` lookup found nothing; a broad `objc_copyClassList` enumeration **crashed the app on launch entirely**, confirmed on a real device). **Actual fix: dropped the native swizzle entirely** — `map_screen.dart` now calls the officially supported `WebKitNavigationDelegate.setOnSSlAuthError()` (mirrors the existing Android `setOnSSlAuthError` call), same fix as SAIMOS Guard (`aa82a11`). Requires `webview_flutter_wkwebview` as a direct `pubspec.yaml` dependency. `WebViewSSLBypass.swift` left in place as a harmless no-op. **Not yet verified on a real device.**
