## What This App Does

This app is **SAIMOS Guard**, a SAIMOS CC fork of the open-source Traccar Client. Its home screen is a WebView embedding the **SAIMOS CC MapStore** web application (see "MapStore WebView (SAIMOS CC)" below for the auth flow and implementation) — that's the primary, user-facing surface of the app.

Underneath that, it's built on Traccar Client: a Flutter GPS tracking app (Android/iOS) that sends device location to a Traccar server. Key capabilities: background tracking via `traccar_client_sdk`, Firebase push commands for remote control, QR code/deep link config import, optional password protection, and home screen quick actions.

## Common Commands

```bash
flutter pub get          # Install dependencies
flutter analyze          # Lint (also runs in CI on every push)
flutter build apk --release   # Android APK (unsigned unless a keystore is configured)
flutter build ipa --release   # iOS (signed IPA; needs code signing configured — see "Build & Release")
```

There are no automated tests — the project relies on static analysis and manual testing. Real builds/releases run on Codemagic, not locally — see "Build & Release" below.

## Architecture

The app is organized into three layers:

**Service layer** (`lib/`)
- `geolocation_service.dart` — thin wrapper around `TraccarClientSdk` singleton; exposes `start()`, `stop()`, `isTracking()`, `requestPosition()`, `getLogs()`
- `preferences.dart` — all config persistence via `SharedPreferencesWithCache`; builds `Config` objects passed to the SDK; Android uses the native SharedPreferences backend for performance
- `push_service.dart` — Firebase Cloud Messaging; handles remote commands (`positionSingle`, `positionPeriodic`, `positionStop`, `factoryReset`) and uploads the FCM token to the server
- `configuration_service.dart` — parses `org.traccar.client://` URIs and HTTP/HTTPS config URLs, applies settings, restarts tracking
- `password_service.dart` — optional password protection stored in SharedPreferences (migrated away from secure storage)

**UI layer** (`lib/`)
- `map_screen.dart` — **the app's home screen**: MapStore/SAIMOS CC WebView; AppBar has refresh and settings icons (settings navigates to MainScreen)
- `main_screen.dart` — tracking toggle card + settings card; reached via the gear icon in MapScreen
- `settings_screen.dart` — all preferences (URL, device ID, accuracy, interval, distance, angle, wakelock, stop detection); contains QR code import entry
- `status_screen.dart` — real-time SDK log viewer, auto-refreshes every 5 seconds, supports share/clear
- `qr_code_screen.dart` — `mobile_scanner` based QR reader; graceful fallback on permission denial

**Infrastructure**
- `main.dart` — initializes Firebase, loads preferences, wires deep links via `app_links`, shows rate dialog
- `quick_actions.dart` — registers home screen shortcuts (start, stop, SOS)
- `firebase_options.dart` — auto-generated by `flutterfire configure`; currently **unused** (`main.dart` calls `Firebase.initializeApp()` without passing `options:`, so init relies purely on the native `google-services.json`/`GoogleService-Info.plist` configs) and stale (still points at the old Firebase project) — do not edit manually, regenerate via `flutterfire configure` if it's ever wired back in
- `lib/l10n/` — 14+ language `.arb` files; English (`app_en.arb`) is the source of truth; run `flutter gen-l10n` to regenerate (handled automatically by build)

## Platform Notes

- Wakelock toggle and the background-location disclosure message are Android-only; gate with `Platform.isAndroid`
- iOS minimum deployment target is 15.0 (set in `ios/Podfile`)
- Android Gradle is configured with 8 GB JVM / 4 GB metaspace in `android/gradle.properties`
- Firebase credentials live in `android/app/google-services.json` and `ios/Runner/GoogleService-Info.plist` — in this fork they **are** committed to the repo (unlike stock Flutter/Firebase project templates, where they're typically gitignored)

## Localization

Add new UI strings only to `lib/l10n/app_en.arb`. Translations for other locales are managed via Transifex (`.github/workflows/translation.yml`). The generated `app_localizations.dart` is committed and should be regenerated with `flutter gen-l10n` after `.arb` changes.

## MapStore WebView (SAIMOS CC)

Implemented in `lib/map_screen.dart` — ported from `C:\_gitea\saimos-cc\traccar-client-android` (`SaimosccWebView.kt`).

- Entry point: **the app's home screen** (MapScreen is `home` in `main.dart`)
- Navigation: settings (gear) icon in the AppBar → MainScreen; no separate "Map" button anymore
- Settings: at the very bottom of `settings_screen.dart` — Control Center server URL, user, password (keys: `saimoscc_url`, `saimoscc_user`, `saimoscc_password`); heading: "SAIMOS Control Center"
- Auth flow: app info → GeoStore login (Basic Auth) → device registration (Talend WS) → user details (XML→JSON) → localStorage injection → load WebView
- Geolocation: auto-granted on Android via `setGeolocationPermissionsPromptCallbacks`; native on iOS
- SSL: HTTP calls trust all certificates (`badCertificateCallback`); the WebView itself bypasses SSL errors via `ios/Runner/WebViewSSLBypass.swift` on iOS (only needed for a self-signed certificate — make sure this file stays registered in `project.pbxproj`, see "Build & Release" for a past incident where it wasn't)
- Reference Android project: `C:\_gitea\saimos-cc\traccar-client-android`

**JDK:** `JAVA_HOME=C:\app\java\jdk-21.0.11+10_x64_jdk` (JDK 21, `javac.exe` present). Android Studio 2026.1.1 is installed.

**Emulator:** VT-x/AMD-V not enabled in BIOS → the x86_64 emulator won't start. Solution: use an ARM64 emulator.
- Emulator binary lives in `emulator_backup\` instead of `emulator\` (Android Studio renamed the folder)
- The existing AVD `Medium_Phone_API_35` (x86_64) can't be used
- **Next step:** install an ARM64 system image (needs an interactive terminal — piping into sdkmanager doesn't work):
  1. `flutter doctor --android-licenses` — confirm all licenses with `y`
  2. `"%LOCALAPPDATA%\Android\sdk\cmdline-tools\latest\bin\sdkmanager.bat" "system-images;android-35;google_apis;arm64-v8a"`
  3. Create the AVD: `avdmanager create avd -n Pixel_ARM64 -k "system-images;android-35;google_apis;arm64-v8a" -d "pixel_6"`
  4. Start the emulator: `"%LOCALAPPDATA%\Android\sdk\emulator_backup\emulator.exe" -avd Pixel_ARM64`

## Build & Release

**App identity (as of 2026-07-25):** Both platforms run under the bundle/package ID `de.mistit.saimosguard`, with their own Firebase project **"saimos-guard"** (project number 616327934228) — no longer Traccar's own `traccar-client-app` project. The internal Android namespace (`org.traccar.client` — Kotlin package structure, MethodChannel names like `org.traccar.client/file_picker`, deep-link scheme `org.traccar.client://`) is deliberately left unchanged; it doesn't need to match `applicationId`.

Builds run on **Codemagic** (CI service, UI workflow editor, no `codemagic.yaml` in the repo). There's no local Mac in the process anymore.

### Local Android build (for testing)

```bash
flutter build apk --debug   # or --release, if a keystore is configured (see below)
```

Install on a connected device (preserves app settings):
```bash
adb -s <device-id> install -r build\app\outputs\flutter-apk\app-debug.apk
```
**Don't** use `flutter install` — internally it does `adb uninstall` + `adb install` and wipes all app data. `adb` lives at `%LOCALAPPDATA%\Android\sdk\platform-tools\adb.exe`.

Note: if `applicationId` ever changes again (e.g. a future rebrand), Android treats it as a completely new app — not an update of the old install, and none of the old settings carry over.

### Android — signed release APK for testers

No keystore exists yet (`android/app/build.gradle.kts` falls back to unsigned without `key.properties`).

1. Generate once, locally (keep the password safe — without the keystore, future updates become impossible):
   ```bash
   keytool -genkeypair -v -keystore saimos-guard-release.jks -keyalg RSA -keysize 2048 -validity 10000 -alias saimos-guard
   ```
2. Store in Codemagic: App settings → Android code signing → upload the `.jks` as a Secure File, passwords/alias as encrypted environment variables
3. Set the workflow build mode to Release (`flutter build apk --release`)
4. After a successful build: download `app-release.apk` from the Codemagic build artifacts and send it directly to testers (no Play Store needed; testers must allow "install from unknown sources")

**Decision (2026-07-26): deliberately not using Google Play for now.** For a new developer account, Google requires a USD 25 one-time fee, a government ID + credit card under the same legal name, *and* — before any production release is even possible — a closed test with at least 12 testers opted in continuously for 14 days, plus a review that takes up to ~7 more days. That's a lot of upfront overhead for internal testing, so direct APK sharing (above) is the path for now. `release.yml`'s GitHub Actions "publishes to Google Play" step (see CI/CD below) isn't part of the current process either — real releases go through Codemagic, not that workflow.

### iOS — TestFlight via Codemagic

**Prerequisites (one-time, already done):**
- `DEVELOPMENT_TEAM` in `ios/Runner.xcodeproj/project.pbxproj` (3 occurrences) = your own Apple Team ID (`grep -n "DEVELOPMENT_TEAM"`)
- `PRODUCT_BUNDLE_IDENTIFIER` (3 occurrences) = `de.mistit.saimosguard`
- App ID `de.mistit.saimosguard` registered in the Apple Developer Portal, **Push Notifications capability enabled** (Identifiers → select the app → check "Push Notifications" → Save)
- App created in App Store Connect (bundle ID must match exactly)

**Codemagic setup:**
1. Create an App Store Connect API key (App Store Connect → Users and Access → Integrations → Keys, role "App Manager"), note the `.p8` file + Key ID + Issuer ID (the file can only be downloaded once)
2. In Codemagic: Team settings → Integrations → App Store Connect → add the API key
3. Workflow: set iOS code signing to "Automatic" with this API key, set the **distribution type to "App Store"** (not "Development" — otherwise the upload fails with error 90161 "Invalid Provisioning Profile")
4. Set the build mode to Release; Codemagic then automatically calls `flutter build ipa --release --export-options-plist ...` (no more manual `--no-codesign`)
5. Enable Publishing → App Store Connect, link the same API key, check "Submit to TestFlight", choose the testing group

**One-time, in App Store Connect:**
- Export compliance question on first upload: choose "Standard encryption algorithms …" (the app only uses regular HTTPS/TLS). To skip this prompt on future uploads, add `ITSAppUsesNonExemptEncryption = false` to `ios/Runner/Info.plist`.
- For **external** testing, a feedback email plus name/phone/email for Beta App Review must be filled in at `https://appstoreconnect.apple.com/apps/<app-id>/testflight/test-info`, followed by an Apple review wait (~24–48h). **Internal** testing (App Store Connect team members) doesn't need this and is available immediately.

**Build number:** Every successful upload to App Store Connect permanently "consumes" the build number (the number after `+` in `version:` in `pubspec.yaml`) — re-uploading with the same number fails with error `ENTITY_ERROR.ATTRIBUTE.INVALID.DUPLICATE` ("bundle version must be higher than the previously uploaded version"), even if the previous TestFlight submission never reached testers for other reasons (e.g. missing test information). Bump the number before every new upload, or enable Codemagic's "Increment build number" option, which does this automatically based on the highest number already present in App Store Connect. The app currently uses its own independent version (`1.0.0+1`) rather than inheriting Traccar's upstream version number — the relationship to the upstream base is tracked via the `saimos-cc/v10.0.7` branch name instead.

**Known gotchas, already fixed (see git history, issue #2):**
- `WebViewSSLBypass.swift` existed on disk but was never registered in `project.pbxproj` (missing PBXFileReference/PBXBuildFile/Sources build phase entries) → "Cannot find 'WebViewSSLBypass' in scope"
- The auto-generated "FlutterFire: flutterfire upload-crashlytics-symbols" build phase script aborted the build when the `flutterfire` CLI wasn't installed on the build machine — the script now checks for it itself and skips the symbol upload instead of failing
- iOS's `WKWebView` sends an incomplete default user agent (missing "Mobile/... Safari/..."), which made MapStore reject it as an unsupported browser — `lib/map_screen.dart` now sets a real mobile Safari user agent on iOS
